# Prediction model documentation

## What is predicted — and what is not

The model estimates **the probability that a configured alert threshold will be crossed within the next 20 readings** for one signal of one device.
It does **not** predict equipment failure: labels are "threshold breach", because that is what the platform can observe. A high probability means "this signal
is heading toward its limit", which is a reason to inspect — not a diagnosis.

## Pipeline (`backend/src/ml/`)

1. The last **20** readings of a signal come from the Redis rolling window.
2. A least-squares line gives the denoised level, slope and volatility (noise).
3. Five features compare these with the machine type's alert limit: headroom to threshold, projected movement over the horizon, projected margin, volatility (residual σ) and trend ÷ headroom.
4. A **logistic regression** turns the features into a probability. Above 50 % a *predictive alert* opens with an estimated time-to-breach; the linear ETA must agree, otherwise the signal is only "elevated".

Per-signal limits come from the alert rules (defaults with per-machine-type overrides), so a CNC machine and a sensor are judged against their own limits.

## Models and scopes

* **Global model** — trained offline on *synthetic* drift / leak / recovery episodes in normalised units (`npm run train`). On held-out synthetic episodes: AUC ≈ 0.94, precision ≈ 89 %, recall ≈ 73 %.
  **These numbers describe the synthetic generator, not real machines**, and the UI labels the model's `source` as `synthetic`.
* **Per-machine-type models** — *Anomaly Prediction → Retrain from telemetry* builds labelled windows from the telemetry that machine type has actually stored.

## Retraining and evaluation

* **Time-ordered split:** train on the oldest 80 %, test on the newest 20 % — never a random shuffle, because shuffling leaks the future into training.
* **Purge gap:** windows whose label horizon overlaps the boundary are dropped so no test label is derivable from training data.
* **Metrics** on the held-out part: AUC, precision, recall, F1, accuracy, Brier score, average lead (readings of warning before a breach) and the positive rate.
* **Validation gate:** a retrained model is activated only if AUC ≥ 0.70 **and** it is not worse than the current model by more than 0.03 on the same data. Otherwise the current model stays active and the reason is shown.
* **Versioning:** every training run — including rejected ones — is stored in `model_versions` with its evaluation, who trained it and why it was or was not activated. An administrator can **roll back** to any earlier version that passed the gate.
* Types without enough labelled data (or without breaches in their history) report "not enough data" instead of producing a meaningless model.

## Explanations

A logistic regression is linear in its features, so each feature's push on the log-odds is **exact** (weight × standardised value). `GET /api/anomaly/explain/:deviceId` and the *Why this risk?* panel show
the contributions, headroom, slope, noise, the model version and its data source. When a rule overrides the raw model (for example the linear ETA disagrees) the panel says so. Nothing in an explanation is generated by a language model.

## Prediction history

Scorings are stored in `prediction_history` (at most one snapshot per device and signal every 30 seconds) — probability, level, time-to-breach, threshold, model version and source, full explanation — kept for `PREDICTION_HISTORY_DAYS`.
It powers the predictive-summary report and the assistant's "what was predicted before" answers.

## Honest limitations

* The demo fleet is produced by the built-in simulator; retrained metrics on simulator telemetry reflect simulated behaviour. With real devices the same pipeline learns real behaviour, but accuracy on real equipment must be measured separately.
* Threshold-breach labels depend on the configured limits: changing a limit changes the problem the model solves (retrain after editing limits).
* A single logistic regression cannot capture interactions between signals; it was chosen because it is fast, runs inside Node, and is fully explainable.
